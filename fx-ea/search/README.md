# 戦略探索エンジン

毎朝、仮説を事前固定プロトコルで検定し、結果を台帳に積む仕組み。

## なぜ「毎朝最良を探す」形にしなかったのか

探索空間を広げるほど偽陽性が増える。この会話で実測した通り:

- DOW族290セルの全数走査で、基準通過は1件(期待誤検出 0.4件)
- 販売ページ基準では 3年窓で18本「合格」するが、翌年運用すると PF 0.96
- 72構成の入れ替え戦略のうち40構成が PF<1.00

**毎朝「今日の最良戦略」を出す仕組みは、毎朝ノイズを報告する。**
そこで、見つけたものを報告するのではなく、**検定した回数を数え続ける**設計にした。

## 必要t値は累積検定数で決まる

| 累積検定数 | 必要t値 |
|---:|---:|
| 1 | 1.64 |
| 10 | 2.58 |
| 100 | 3.29 |
| 1,000 | 3.89 |
| 10,000 | 4.42 |
| 100,000 | 4.89 |

参考: この会話で最も強かった NAS100 月曜L は **t=3.42**。
つまり **1,000回検定した後では通らない**。探索を続けるほど基準が上がる。
これは仕様であって不具合ではない。

## 使い方

### 1. 仮説を追加する

`hypotheses.json` の `queue` に追記する:

```json
{
  "id": "zrev-idx-w10-t15-h2",
  "note": "指数 z(10) 1.5SD 逆張り 2日保有",
  "family": "zrev",
  "params": {"symbols": ["US500","NAS100","GER40"],
             "win": 10, "thr": 1.5, "hold": 2, "direction": 1},
  "space_size": 90,
  "status": "pending"
}
```

**`space_size` は「この仮説にたどり着くまでに裏で何通り検討したか」**を書く。
銘柄3 × 窓5通り × 閾値3通り × 保有2通り を眺めて1つ選んだなら 90。
ここを正直に書かないと必要t値が甘くなり、仕組み全体が意味を失う。

### 2. 実行

```
python3 run.py            # pending をすべて検定し、台帳に記録
python3 run.py --report   # 検定せず、台帳の要約だけ出す
```

結果は `REPORT.md`、履歴は `ledger.json`。

### 3. 台帳は消さない

同じ仮説を条件だけ変えて再投入すると累積検定数が増え、必要t値が上がる。
**こっそりチェリーピックできない**のが台帳の目的。

## 判定プロトコル v2(事前固定)

| 基準 | 内容 |
|---|---|
| 最低取引数 | 100(未満は「検証不能」) |
| **補正t値** | **t / √hold** が累積検定数に応じた Bonferroni 閾値以上 |
| IS/OOS | 前半60%・後半40% の**双方**でプラス |
| ウォークフォワード | 各年、それ以前のデータだけで平均プラスだった年のみ採用し、その合計がプラス |
| **対ベンチマーク** | **同一銘柄・同一保有日数の「常時買い持ち」を上回ること** |

5つすべてを満たして初めて「通過」。

### 日次t診断(基準ではない)

`t/√hold` は**保有期間の重複しか補正していない**。同じ日に相関の高い複数銘柄を
建てている分は補正されないため、多銘柄合成の仮説は t が過大に出る。

そこで全エントリに `n_dates`(同一日を1観測に集約したときの日数)と
`t_date`(その集約後の補正t)を**診断値として**記録している。

| | 記録上の n | 補正t | 日数 | 日次t |
|---|--:|--:|--:|--:|
| `volregime-idx` | 10,995 | 3.59 | 2,850 | **1.18** |
| `breadth-idx-washout` | 5,327 | 4.29 | 772 | **1.89** |

**判定基準は5つのまま。ただし `t_date` が必要t値を下回る仮説は「見つけた」と
報告してはいけない。** 必ず `attack.py` にかけること。

## 通過候補を潰す — attack.py

```
python3 attack.py <hypothesis-id>
```

台帳にある仮説を、逆方向・フィルタなし対照・年別・日次集約・局面集約の
5つの角度から検査する。HANDOFF.md 3節のチェックリストの機械化。

### なぜ補正t値とベンチマークを入れたか(2026-08-27 v2)

初回の拡張検定で `volregime-idx`(指数8銘柄・高ボラ局面のみロング・5日保有)が
**生t=8.03 で通過**した。検証したところ偽の発見だった:

| 構成 | n | 平均 | t |
|---|--:|--:|--:|
| 高ボラのみロング | 10,995 | 21.96bp | 8.03 |
| **常時ロング(フィルタなし)** | 29,997 | 12.71bp | **8.98** |
| 高ボラのみ**ショート** | 10,995 | −39.96bp | **−14.62** |

フィルタなしの方が t が高く、ショートでは大きく負ける。
**局面効果ではなく単なる指数ロング**だった。

原因は2つ:

1. **建玉の重複**。日次シグナル × 5日保有では隣り合う取引が4/5重なり、
   独立でなくなって t 値が過大になる。→ `t/√hold` で補正
2. **方向性エクスポージャーとエッジの混同**。上昇バイアスのある資産を
   買い持ちすれば、どんなフィルタを噛ませても数字は出る。
   → 同一銘柄の常時買い持ちを上回ることを必須にした

補正後: 生t 8.03 → **補正t 3.59** < 必要4.25 で棄却。台帳も再判定済み。

## 2つのトラック

| | 売買トラック(EA用) | 指標トラック(インジケーター用) |
|---|---|---|
| 当てにいくもの | 翌日の**方向** | 翌日の**変動幅**・いまの**局面** |
| 族 | 24族(下記) | `rangefc` `volpersist` `dowrange` |
| 判定 | 判定プロトコル v2 | 指標プロトコル v1 |
| 対照 | 同一銘柄の常時買い持ち | その銘柄の過去平均(素朴基準) |
| 仮説の書き方 | 既定 | `"track": "indicator"` を付ける |

累積検定数は**共有**する。見た回数は同じ台帳で数える。

**方向は46件すべて棄却。変動幅は通る。** 同じデータでも、当てにいく対象を
変えると結果が変わる。インジケーターは方向を当てる必要がない商品なので、
このトラックの通過はそのまま商品の根拠になり得る。ただし
**「方向を当てられる」という意味には絶対にならない。**

### 指標トラックの族

| family | 内容 | 主なパラメータ |
|---|---|---|
| `rangefc` | 翌日の高安幅を素朴基準より当てられるか | `n` `kind`(sma/atr/ewma/last) |
| `volpersist` | 「いま荒れている」に中身があるか | `n` `q` |
| `dowrange` | 「この曜日は動きやすい」に中身があるか | `dow` |
| `effratio` | 「いまトレンドが出ている」に中身があるか | `n` |
| `gapsize` | 「明日の寄りはどれくらい飛ぶか」 | `n` `kind` |
| `interval` | 値幅の**範囲**の示し方に中身があるか | `n` `lo` `hi` |
| `quiethit` | 「静か」「荒い」判定の的中率が無条件より高いか | `n` `base_bars` `thr` `side` |

**`effratio` は測ると大きくマイナスに出る**(FX −38.1% / 指数 −38.9%、
どちらも改善年 0/15)。トレンド判定の表示には中身がない。詳細は HANDOFF 2.62節。
目的変数が「次の n 本」の族は、素朴基準の積み上げを n 本遅らせないと
素朴基準側だけが未来を覗くので注意。

戻り値の形が売買の族と違う: `[(日付, 改善, 素朴基準の大きさ)]`。
**改善 = 素朴基準の誤差 − 予測の誤差。**

仮説に `"tf": "W"` を付けると、日足を週足にまとめてから検定する
(`engine.resample_weekly`)。日中足は取れないが上位足なら作れる。
週の最後のバーは途中までしかないので落としている。

**`kind="atr"` は注意。** ATRは真の値幅(ギャップ込み)なので、高安幅の予測に
使うとギャップの大きい銘柄で系統的に上振れする。実測で USDJPY −16.4% /
JP225 −11.4% と、素朴基準より**悪化**した。予測対象と同じ高安幅で組んだ
`kind="sma"` にすると20銘柄すべてプラスになる。

### 指標プロトコル v1(事前固定)

| 基準 | 内容 |
|---|---|
| 最低観測数 | 100 |
| 補正t値 | 改善の t/√hold が累積検定数のBonferroni閾値以上 |
| IS/OOS | 前半60%・後半40%の**双方**で改善プラス |
| 年別一貫性 | 改善が正の年が**全年の80%以上** |
| 実用水準 | 平均改善 ÷ 平均素朴基準が**5%以上** |

## 通過した知見を商品にする — mirror_rangemeter.py

```
python3 mirror_rangemeter.py --evidence
```

**出荷する MQL5/MQL4 の `Recalc()` を Python に写したもの。**
販売ページに載せる数値は、台帳の検定値ではなく**これが出した数値**を使う。
台帳の素朴基準は「全履歴の拡大平均」、製品は「直近3,000本の平均」で、
基準が違うため数字も違う。小さいほうを載せる。

`--evidence` で `../indicator-next/EVIDENCE.md` を生成する。手で書き換えないこと。

商品は `fx-ea/indicator-next/`(定石 参 ─ 値幅計)。

## 商品の主張を実データで確認する — firerate.py / quadra_check.py

```
python3 firerate.py
```

出品する商品が商品概要に書いている発火頻度を実測する。
現在の対象は 定石弐 待ち伏せ の「1通貨ペアあたり年に数回」。
**実測 年3.6回/ペアで主張どおり。**

```
python3 quadra_check.py
```

同じく弐の「3条件に緩めると9通り全滅」の確認。
**再現しなかった**(3条件でも保有日数5通りすべてでプラス)。
ただし4条件・3条件ともノイズと区別がつかない水準。詳細は HANDOFF 2.69節。

条件は説明文ではなく `indicator/MQL5/定石弐_待ち伏せ.mq5` の `EvalDay` に
合わせること(当日変動は前日終値比・標準偏差は標本)。説明文から起こすと
桁が変わる。仮説の検定ではないので台帳には加算しない。

### 条件の合流(combo)

| family | 内容 | 主なパラメータ |
|---|---|---|
| `combo` | 複数の条件が同じバーで**すべて**揃った翌日に建てる | `conds` `direction` `hold` `need` |

`conds` は `conditions.py` の述語のリスト:

```json
"conds": [{"k":"rsi","n":14,"op":"<","thr":35.0},
          {"k":"z","win":20,"op":"<","thr":-1.5},
          {"k":"streak","run":3,"dirn":-1},
          {"k":"ret","op":"<","pct":-0.5}]
```

使える条件は `rsi` `z` `streak` `ret` `vol` `range`。
`need` を指定すると「n個中k個」でも建てる(条件を緩めた対照用)。

**種別キーは `"k"`。** 条件側の引数に `k` を使わない(`streak` は `run`、
`range` は `mult`)のはそのため。条件の列は銘柄ごとにメモ化している。
| `ccystr` | 通貨強弱の断面 最強通貨買い・最弱通貨売り | `symbols` `look` `hold` |

### 出来高系
| family | 内容 | 主なパラメータ |
|---|---|---|
| `volspike` | 出来高が n 日中央値の k 倍超の日 | `n` `k` `mode`(follow/fade) `hold` |

**出来高は FX では使えない。** Yahoo は FX の volume を常に 0 で返す。
指数・商品でのみ有効で、AUS200(60%)と XPTUSD(58%)は欠損が多いため除外している。
日足の行は `[日付, 始, 高, 安, 終, 出来高]` の6要素(2026-08-27 に出来高を追加。
5要素だった旧キャッシュは自動で取り直す)。

`nr`(ボラ収縮→方向追随/逆行、`n` `look` `mode` `hold`)は構造系に含む。

**`lead` の時刻整合に注意。** src の確定終値が tgt の建玉時刻(翌営業日の寄り)より
前に来る組み合わせでしか使えない。米指数の引け(20:00 UTC)→ 翌日のアジア指数・FXの寄り
は成立するが、FXの日足終値(00:00 UTC)→ 同時刻の指数の寄り は先読みになる。

**参照専用シンボル**(`engine.REFS`。建玉は作らない):

| 名前 | Yahoo | 使い道 |
|---|---|---|
| `VIX` `VVIX` `SKEW` | ^VIX ^VVIX ^SKEW | オプション市場 |
| `US3M` `US5Y` `US10Y` `US30Y` | ^IRX ^FVX ^TNX ^TYX | 金利の水準と期間構造 |
| `COPPER` | HG=F | 景気の代理(銅/金 比など) |

`xfilter` の `ref`(単一系列の水準)と `xspread` の `a`/`b`(系列間の関係)に使う。
なお `^VIX3M` は Yahoo が1行しか返さないため使えない。

`params` に `symbols`(リスト)を渡すと合成、`sym`(単体)を渡すと単一銘柄。
指標は `indicators.py`、族の実装は `families.py`。

## コスト前提

往復(名目比%): FX 0.020 / 指数 0.030 / 貴金属 0.050 / エネルギー 0.060 / 暗号資産 0.100
1泊追加保有ごとに FX +0.004 / 指数・貴金属 +0.015 / エネルギー +0.018 / 暗号資産 +0.030

**エキゾチック通貨(TRY/ZAR/MXN)は universe に入れない。** 損益のほとんどが
スワップで、このエンジンはスワップを測れない。測れないものを検定しない。

`pairs` は**2脚それぞれ**のクラスで、保有日数分のキャリーを含めて控除する
(2026-08-27 修正。それ以前は片脚の往復コストのみでキャリーを引いておらず、
WTI/Brent スプレッドの平均が 40.4bp → 26.0bp、PF 1.71 → 1.41 に下がった。
`pairs-eur-gbp` `pairs-aud-nzd` `pairs-xau-xag` は修正前の値で記録されているが、
いずれも修正すればさらに悪化する方向のため再検定していない)。

## データの限界(重要)

データは **Yahoo Finance の日足**。以下は測れない:

- **日中の時刻依存**(定石壱の「サーバー時間月曜4時」など)。日足の始値は
  FXでは 00:00 UTC、指数では現物の寄りであり、MT5の日足始値とは別物
- **実スプレッドの時間変動**(ロールオーバー時間帯の拡大など)
- **業者ごとのスワップ**
- **スプレッドそのもの** — Yahooの日足に入っていない。
  したがって **定石零 環境計の中核主張(時間帯別の割高度)はこのエンジンでは
  検証できない**。実機のMT5実測が唯一の手段(既にユーザーが実施済み)

したがって `dow-jpy-mon`(円クロス月曜)がこのエンジンで棄却されても、
**定石壱が否定されたわけではない**。壱はMT5のH1実データ・サーバー時刻基準で
別途検証済み(1,636取引 / PF 1.304)。
このエンジンは**日足で表現できる仮説の一次スクリーニング**であり、
通過したものはMT5で再検証する必要がある。
