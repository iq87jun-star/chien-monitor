# バイナリーオプション 統計的エッジ検証フレームワーク

対象: IG証券バイナリーオプション（0–100ポイント建て、判定時に 100/0 で清算）。
種別: ラダー（finish-above/below）/ ワンタッチ / レンジ。
通貨ペア: USDJPY, GBPJPY, EURJPY, AUDJPY, EURUSD, GBPUSD, AUDUSD。
時間: 1日12回・各回2時間毎、最短60秒〜。

> 本フレームワークは「願望」ではなく**コスト（スプレッド）控除後の期待値が正かどうか**だけを判定するために作られている。
> エッジが見つからなければ「見つからない」と結論することを設計目標とする。フィッティングで無理に作らない。

---

## 0. 大前提（明文化）

1. IGの提示価格 P（ポイント, 0–100）は「市場の勝率推定 + IGスプレッド/マークアップ」を織り込む。
   - すなわち提示mid ≈ `100 × p_market`（市場が見る成就確率）に、IGの利益マージンが上乗せされる。
2. **損益分岐勝率 ≈ P/100**。スプレッド分だけ理論より不利。
3. 利益化の必要十分条件は「自分の勝率推定が継続的に P/100 を上回る（売りなら下回る）エッジの存在」。
4. エッジが見つからなければ「無い」と結論する。

---

## 1. 期待値の式と損益分岐勝率の導出

清算は YES=100 / NO=0。提示は bid `B`（売り執行値）/ ask `A`（買い執行値）, スプレッド `s = A − B`。

### 1.1 買い（YES を ask A で買う）
- 勝ち（YES成就, 確率 p）: 損益 = `100 − A`
- 負け（確率 1−p）: 損益 = `−A`
- **期待値（ポイント）= `100p − A`**
- **損益分岐勝率 `p* = A/100`** → `p > A/100` で EV>0

### 1.2 売り（YES を bid B で売る）
- YES不成就（確率 1−p）: 損益 = `+B`
- YES成就（確率 p）: 損益 = `−(100 − B)`
- **期待値（ポイント）= `B − 100p`**
- **損益分岐勝率 `p* = B/100`** → `p < B/100` で EV>0

### 1.3 ノートレード帯とスプレッドコスト
- `B/100 < p < A/100` の範囲は**売りも買いも EV<0**（取引してはいけない帯）。
- mid `M = (A+B)/2`、半スプレッド `s/2`。自分の推定 p が市場mid（`p_market = M/100`）と一致するなら
  - 買いEV = `100p − A = 100·p_market − M − s/2 = −s/2`（必ず半スプレッド負け）。
- **必要な確率エッジ**: 買いを正当化するには
  `100p − A > 0` ⇔ `δ ≡ p − p_market > s/200`。
  例) s = 6 ポイント → 必要エッジ δ > 0.03（=3%ポイント）。**これは小さくない。**

> 結論の出発点: 「mid に対して 3% ポイント前後の確率予測優位を“継続的に”出せるか」が全て。
> FXの 60秒〜2時間という地平でこれを安定して出すのは極めて難しい、という強い事前分布から始める。

## 2. IG実スプレッド幅の推定・計測方法

エッジ判定はコスト控除後で行うため、スプレッドの実測が生命線。

### 方法A: 直接気配採取（最優先・唯一の厳密法）
- IGプラットフォームの各銘柄（種別×ストライク×残存時間）について bid/ask スナップショットを時系列収集。
- `s = A − B` を **(種別, moneyness, 残存時間, 時間帯, ボラレジーム) 別に**集計（中央値・分布）。
- 残存時間が短いほど、流動性が薄いほどスプレッドは拡大する傾向 → バケット別が必須。

### 方法B: モデル相対（マークアップの分解, 直接採取の補助）
1. 原資産のティック/1秒mmidからフェアバリュー `F = 100 × p_model` を算出。
2. `markup_skew = M − F`（midの偏り = IGの理論からの乖離）。
3. `[B, A]` が `F` をどう挟むか → スプレッドとスキューを分離。
- 注意: これは**モデル誤差とマークアップが混ざる**。Bの代用にはならず、あくまでAの裏取りに使う。

実装: `spread.py` の `estimate_spread`, `decompose_markup`。

## 3. エッジ候補仮説（なぜ歪みが生じうるか）

IGはマーケットメーカーであり、価格 = 内部モデル + マージン + 在庫管理。
**歪みの源泉は「モデルの簡略化」**（定数ボラ・無ジャンプ・日内季節性無視・更新遅延）に限られる。
各仮説は「なぜ歪むか」と「なぜ歪みが取れない/取りにくいか」を併記する。

| # | 仮説 | 歪みが生じうる根拠 | 取りにくさ（反証要因） |
|---|------|------------------|----------------------|
| H1 | ボラ・レジーム誤価格 | IGの実装ボラがスティッキー/ラグだと、GARCH的クラスタリングで予測可能な実現ボラとの乖離が touch/ladder を誤価格化 | 乖離が出る局面ほどIGはスプレッドを広げる |
| H2 | 日内ボラ季節性 | 東京/欧州/NY重複でボラが規則的に変動。IGが時間帯で定数ボラを使うと、高ボラ時間帯の touch が割安・閑散時間帯が割高 | 季節性は周知で価格に織り込まれやすい |
| H3 | 経済指標前後 | 指標（雇用統計/CPI/中銀）のジャンプリスクを定常拡散ボラが過小評価 → touch 割安 | IGは発表時に提示停止/スプレッド急拡大/約定拒否しやすい |
| H4 | 短期ミーンリバージョン/モメンタム | マイクロ構造上のサブ分単位の反転 | 効果がスプレッド未満で消える |
| H5 | 提示更新遅延（レイテンシ） | スポット急変時にオプション提示が追随遅れ → 遅れた側を取れる | **IGが最も防御する**。リクオート/約定取消の対象になりやすく、ライブで再現しない可能性大 |
| H6 | ラウンドナンバー/心理的節目 | レンジ境界が節目に集中する偏り | 効果が弱く不安定 |

> どの仮説も「歪みうる理由」と同程度に「取れない理由」がある。これが本質。

## 4. バックテスト設計

### 4.1 データ要件（最重要・制約条件）
| データ | 粒度 | 必須度 |
|--------|------|--------|
| 原資産スポット bid/ask | ティック〜1秒 | 必須 |
| **IGバイナリ実気配 (bid/ask, strike, expiry, type)** | 意思決定時刻のスナップショット | **これが無いと厳密検証不能** |
| 清算結果 (0/100) | 各オプション | 必須 |
| 経済指標カレンダー | 時刻 + サプライズ量（実績−予想） | H3に必須 |
| 実現ボラ/特徴量 | 派生 | 必須 |

> **率直な制約**: IGの「過去の実提示気配」が無ければ、できるのは
> 「フェアモデル + 仮定スプレッド」での*仮説的*検証に留まる。
> その結果は「もしスプレッドが s ならエッジは X」という条件付きにすぎず、ライブ保証ではない。
> 本コードは仮定スプレッドモードと実気配モードの両方を扱うが、結論の強さは実気配の有無で大きく変わる。

### 4.2 ウォークフォワード / アウトオブサンプル
- ローリング: 学習6ヶ月 → 検証1ヶ月、1ヶ月ずつ前進（`backtest.walk_forward`）。
- 最終ホールドアウト（一度も触らない）を別に確保。
- ボラ推定・閾値などの全パラメータは学習窓のみで決定（先読み禁止を強制）。

### 4.3 多重検定の補正
- 試した仮説数 N を必ず記録。
- Benjamini-Hochberg FDR（`stats_tests.benjamini_hochberg`）。
- **Deflated Sharpe Ratio**（Bailey & López de Prado, 試行数と非正規性を補正; `stats_tests.deflated_sharpe_ratio`）。
- 自己相関を尊重する **ブロックブートストラップ**で平均EV/トレードの信頼区間。

### 4.4 評価指標（すべてコスト控除後）
- トレードあたり平均EV（ポイント, **スプレッド込みの実約定値で計算**）。
- 実勝率 vs 損益分岐 `P/100`。
- ブートストラップ95%CI、P&LのSharpe、プロフィットファクター、最大DD。
- **スプレッド控除前の見かけ成績は一切成果として扱わない**（コードは控除後のみ報告）。

## 5. リスク管理（必須要件）

- **固定比率**: 1取引の最大損失 = 口座資金の小さな固定% (`risk_fraction`、既定 0.5%)。
  - 買いの1枚あたり最大損失 = 支払額 A。枚数 = `floor(risk_fraction × equity / max_loss_per_unit)`。
- **ドローダウン上限**: 例 15% 到達で全停止・再評価（`risk.DrawdownGuard`）。
- **連敗サーキットブレーカー**: 連敗 N 回で当日停止。
- **ケリー**: `f* = (100p − A)/(100 − A)`（買い）。推定誤差を考え**フラクショナル（1/4）**のみ。エッジ不確実なら使わない。
- **マーチンゲール等の倍賭けは明示的に禁止**（`risk.MartingaleGuard` が違反で例外送出）。

### なぜマーチンゲール禁止か（理由）
- 負け後に賭金を倍化すると賭金が幾何級数的に増大 → 有限資金では必ず資金上限を超える賭けが要求され、**破産確率が上昇**（負/ゼロEVでは破産確率→1）。
- 期待値は改善しない（むしろ手数料分悪化）。多数の小勝を稀な巨大損に変換し、**分散と破産リスクのみを最大化**する。エッジの有無を変える手段ではない。

## 7. 結論の出し方（正直さの要件）

最終報告 (`backtest.summarize`) は必ず以下を併記する:
1. コスト控除後の検出エッジの有無と符号。
2. 統計的信頼度（ブートストラップCI, BH-FDR後のp値, Deflated Sharpe）。
3. 過剰最適化の懸念（試行数、IS/OOS差、パラメータ感応度）。
4. ライブ劣化要因（スプレッド拡大・約定拒否/リクオート・スリッページ・指標時の提示停止・H5の防御）。

**事前分布としての結論**: (a) IGがスプレッド+マークアップを織り込み、(b) FXは60秒〜2時間で近似効率的、
(c) 最も妥当な歪み（H5レイテンシ）はIGが能動的に防御し、(d) IG実気配無しでは検証は仮説的——
以上から「**コスト控除後に頑健で実取引可能なエッジは存在しない可能性が高い**」を出発点とする。
見かけのエッジは過剰最適化か取引不能である蓋然性が高い。データが反証した場合のみ、その強さに応じて慎重に結論を更新する。
