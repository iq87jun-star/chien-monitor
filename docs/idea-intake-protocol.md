# アイデア募集プロトコル — 発散と実行の分離

**ステータス**: 発効
**目的**: 「思いつき → 即席バックテスト → p-hacking」の経路を構造的に遮断する。

---

## 1. 大原則: 発散と実行の分離

| フェーズ | 担当セッション | 権限 |
|---|---|---|
| 発散 | 募集セッション | アイデア出し・トリアージ **のみ** |
| 実行 | 検証セッション | 事前登録済みの仮説のバックテストのみ |

- **募集セッションにはバックテスト実行権を与えない。** データの読み込み・集計・「ちょっと見てみる」も実行に含む。禁止。
- **実行の門番は事前登録**(docs/114 以降の事前登録書式)。事前登録を通過していない仮説は、いかなる理由でもバックテストしない。
- 募集セッションの成果物は「アイデア一覧 + トリアージ結果」であり、数値的な検証結果を一切含まない。

## 2. 受付レーン(この4つ以外は受け付けない)

| レーン | 内容 | 追加要件 |
|---|---|---|
| **L1 器・実装系** | 検証済み5本の新しい載せ方(執行・合成・タイミングの改良) | なし。最速で採用可能なレーン |
| **L2 新データ源** | 限月別先物・オプションIV・個別株・COT 等の新規データ | **入手手順(取得元・形式・コスト・更新頻度)まで書けない案は不可** |
| **L3 既存機序の隣接仮説** | 検証済み機序の近傍にある未検証仮説 | **棄却済み領域チェック必須**(§3) |
| **L4 運用・資金系** | 口座構成・スケーリング・資金配分 | なし |

レーンに分類できない案は、その場で却下し、却下台帳(§4)に記録する。

## 3. 自動却下トラップ(却下は裁量ではなく規則)

以下に該当する案は**議論せず自動却下**する:

1. **棄却済み領域への回帰** — 以下は検証済みで棄却されている(docs/14〜93、docs/107):
   - FX 日中 H1 系
   - 月末月初(turn-of-month)系
   - キャリー系
   - 商品 TSMOM 系
   - その他 docs/14〜93、docs/107 に記録された棄却領域
2. **同じデータ宇宙の再探索** — 既に探索済みのデータ宇宙(同一データ・同一頻度・同一対象)を、パラメータや切り口を変えて再探索する案。切り口の変更は新しい仮説ではない。

**各アイデアに「棄却済み領域チェック欄」を必須化する。** 空欄・「該当なし(未確認)」の案は受理しない。提案者(セッション)が該当 docs 番号まで確認して初めてチェック済みとみなす。

## 4. 却下案も記録する(negative space 資産)

- 募集セッションは **20案** 出させ、トリアージで **上位3案のみ詳細化** する。
- **却下した17案も一覧で保存する**(却下理由・該当トラップを1行ずつ)。
- 「考えて捨てた」の地図が将来の再発明を防ぐ。却下台帳はこのプロジェクトの negative space 資産の続きである。

## 5. F2 の教訓(統計的規律)

- **p値が良いだけの提案は不可。** 機序(なぜエッジが存在し、誰が反対側で損をしているか)の説明がない案は詳細化に進めない。
- **プラセボ検査を常に想定する。** 「ベータの言い換え」検査 — 提案のリターンが既知のベータ(市場・キャリー・モメンタム等)の言い換えで再現できるなら、それは新しいエッジではない。詳細化の段階でプラセボ設計を明記すること。

## 6. 運用フロー

```
募集セッション                          検証セッション
─────────────                          ─────────────
20案を出す
  ↓
自動却下トラップ適用(§3)
  ↓
レーン分類(§2)・却下17案を台帳へ(§4)
  ↓
上位3案を詳細化(テンプレート使用)
  ↓
事前登録書式に転記(docs/114以降) ──→  事前登録レビュー通過後のみ
                                         バックテスト実行
```
