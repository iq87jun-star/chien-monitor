## 1. データ(固定)

- **Dukascopyティック**: EURJPY / GBPJPY / USDJPY
- **月曜と火曜のみ・03〜12時UTC**(v7のエントリー窓04-10とその前後、および24h後の決済窓)
- 窓: **2023-07-01〜2026-06-30(直近3年)** — 執行最適化には現行のマイクロ構造だけが関係する
  (10年前のスプレッドは今日の執行に無関係。エッジ検定ではないためpre-2016は不要)
- 保存: 1分足(bid中央値/ask中央値/スプレッド中央値/ティック数)に集約(Drive ≈ 20-30MB)
- 推定取得量: 3ペア×2曜日×10時間×156週 ≈ 9,400ファイル(Colabで30〜60分・再開可能)

## 2. 検定項目(事前固定・追加禁止)

- **H20a(スプレッド実測)**: 月曜03-12時UTCの時刻別スプレッド分布(中央値/p90)。
  検証で仮定した往復コスト(円ペア≈1.3-2.0bps)と、EAの`InpMaxSpreadPips=3.0`の妥当性を実測で採点。
- **H20b(エントリー時刻セットの執行頑健性)**: 現行 {04,06,08,10} に対し、事前列挙した代替
  {03,05,07,09} / {05,07,09,11} / {04,06,08,10}(基準) の3セットのみを、**実bid/ask**での
  エントリー(ask)→24h後決済(bid)で比較。シグナルは不変(月曜LONG・等分割)。
- **H20c(スプレッド上限の校正)**: エントリー時刻の実測スプレッド p95 から `InpMaxSpreadPips` を
  防御的に再設定(EV主張なし・見送り頻度の実測付き)。

## 3. 決定規則(事前固定)

1. **時刻セット変更(H20b)**は、代替セットが**3年すべての年次で**実コスト後netが基準セットを上回り、
   かつ改善幅がスプレッド差で説明できる場合のみ提案(単年・単ペアの上振れでは動かさない)。
   提案止まり=実装はユーザー承認+デモ後。
2. **`InpMaxSpreadPips`(H20c)**は実測p95×1.2に更新提案(防御パラメータ・エッジ主張なし)。
3. H20aで実測往復コストが検証仮定の**2倍を超える**場合、v7/v9の検証済みnetの再解釈
   (コスト感応の再計算)を docs/109 に記載する — 数字を盛らない方向の修正はゲート不要で即時。
4. 月曜03-12時の**リターン系の新パターン探し(時刻別ドリフト等)はやらない** —
   それは執行最適化ではなく同宇宙の再探索であり禁止(docs/80)。

## 4. 手順

1. Colabで `research/colab_edge20_tick_fetch.py` を実行(Driveマウント・再開可能)
2. 同Colabで `research/edge20_tick_execution.py` を実行 → `edge20_tick_execution.json` 出力
