# 102. レジーム監視の自動化 — 24ヶ月ローリング純益の符号判定と早期警報(事前定義)

> docs/99 依頼B-6。docs/86 §2「v4/v7/E-Monは現行レジーム現象 → 直近24ヶ月ローリングnetの符号監視を
> 運用カードに追加すべき」の実装。スクリプト: `research/regime_monitor.py`(毎月初に実行)。
> 出力: `research/results/regime_monitor.json`。

## 1. ★警報条件(事前定義 — 以後の変更は事前登録扱い・本docの改訂が必要)

| 状態 | 条件(月末確定ベース) | 事前定義の行動 |
|---|---|---|
| **GREEN** | 24Mローリングnet > 0 | 通常運用 |
| **YELLOW** | 24Mローリングnet ≤ 0(初回) | 該当スリーブの**新規サイズを50%へ**(EA入力の該当リスク%を半分)。翌月再判定 |
| **RED** | 24Mローリングnet ≤ 0 が**2ヶ月末連続** | 該当スリーブを**新規停止**(建玉は自然決済)。復帰条件=24M netが正へ回復 |

- 判定は**月末確定分のみ**(進行中の当月は除外)。補助表示: 12M net(警報には使わない)。
- ⚠ データはYahoo日足近似のローリング窓。**符号のみ**を使う設計だが、YELLOW/RED発火時は
  必ずDrive(Dukascopy)で再確認してから行動する(誤警報での過剰反応を防ぐ)。
- 事後choose防止: 閾値(0)・窓(24M)・連続数(2)は docs/86 §2 の含意から**この初版で固定**。
  変更したくなったら「変更案→理由→docs改訂」の順(いじった後に正当化しない)。

## 2. 初回実行(2026-07-02, 判定=2026-06月末まで)

| スリーブ | 状態 | 24M net | 12M net | 履歴中の24M負月数/総月数 |
|---|:-:|--:|--:|--:|
| v4 | **GREEN** | +10.66% | +12.11% | 2/100 |
| v7 | **GREEN** | +4.44% | +2.17% | 13/103 |
| E-Mon[RG3] | **GREEN** | +9.74% | +2.83% | 15/98 |
| E5(参考) | GREEN | +20.74% | +3.55% | 39/102 |

- **全スリーブGREEN=現行レジーム継続**。v7の24M netが+4.4%と3本中最薄=最初に監視が効くのはv7の可能性が高い
  (docs/84の「pre-2016無効」とも整合的な、最もレジーム依存度が高いスリーブ)。
- 「履歴中の負月数」は過去にもYELLOW相当が起きていたことを示す(v7 13回/E-Mon 15回)=
  **単発YELLOWは歴史的に珍しくない**。だからこそ行動は半減にとどめ、REDの2連続で初めて停止する設計。

## 3. 運用手順(月次ルーチンに追加)

1. 毎月初: `python3 research/regime_monitor.py`(要ネット。約1分)
2. 全GREEN → 何もしない。JSONの日付だけ確認。
3. YELLOW/RED → Drive再確認 → 事前定義の行動(§1) → docs/98に行動を記録。
4. 半年ごと(6月/12月): docs/101 の相関更新もあわせて再実行。

> 免責: 本モニタは早期警報であり、レジーム転換の予知ではない(転換は事後にしか確定しない)。
> 警報が出ないことは将来の安全を保証しない。年次生存確認(docs/78 フェーズ5-21)は別途継続。
