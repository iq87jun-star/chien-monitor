## 追補1 (2026-11-04): 事前登録(データを見る前に固定)
- データ: Gamma API の解決済み市場(出来高 ≥ $10k)。一覧は offset 上限 2,000 のため end_date の月次窓(2024-01〜2026-12)で分割取得(38,415 件)。CLOB API の YES トークン時間別価格履歴(fidelity 60 分)。解決は outcomePrices(1/0)。
- H1 ロングショット過大評価: 解決の T 日前(T=1, 3, 7, 30)に YES 価格 p が 0.02〜0.10 の市場で実現 YES 率 q を測る。q < p なら NO 買い(費用 1−p、利益 p)に優位。
- H2 本命の過小評価: p ≥ 0.90 で q > p なら YES 買い。
- H3 時間減価: T=7→1 の価格推移を解決側別に。
- 判定: 全期間と前半/後半で符号・大きさが保たれ、カテゴリ(政治/スポーツ/暗号資産/他)別に崩れず、スプレッド(価格帯別の実測: 流動市場で 0.1〜0.7c、最大 1.5c)控除後も正であること。
- 実行面: 板の深さ(best±1c で $3,500〜4,600)、negRisk 市場の構造、UMA 解決の裁量リスク、USDC の入出金経路、税務(雑所得)。
- 段階: (1) 価格系列で H1〜H3 → (2) 合格なら紙上→$50 単位のフォワード → (3) 発注ボット(py-clob-client)。
- スクリプト: `scripts/collect.py`(一覧+履歴、初版)、`scripts/collect2.py`(月次窓で一覧を取り直し+残りの履歴)、`scripts/analyze.py`(H1〜H3)。データは scratchpad(`poly/markets.jsonl`、`poly/ph/*.json`)に置き、リポジトリには入れない。

## 追補2 (2026-11-04): 予備結果(2026-10〜11 の 2,044 市場のみ。全期間は収集後に差し替え)
- 2〜5c(T=7): p 0.032 / q 0.011 → NO 買い純益 +1.6%。方向は仮説どおりだが利幅は小さい。
- 95〜98c(T=7): n=192 全件 YES → YES 買い +3.0%/7 日、T=30 でも +3.3%。1 回の外れで −100% のため n=192・外れ 0 では裾を押さえられない。
- 20〜80c は前半/後半で符号が反転し優位なし。

## 追補3 (2026-11-04): 全期間検証の前に固定する操作的定義(全期間データの結果を見る前に記録)
追補1 のゲートは「符号・大きさが保たれ」「崩れず」の運用が未定義だったため、全期間の集計を見る前に以下で固定する。仮説・価格帯・T・コスト 0.5c は追補1/`analyze.py` のまま変えない。
- **判定単位**: (戦略, 価格帯, T)。H1 = NO 買い × {0.02–0.05, 0.05–0.10}、H2 = YES 買い × {0.90–0.95, 0.95–0.98, 0.98–1.00}、T ∈ {1, 3, 7, 30}。計 20 単位を全部報告する(良いものだけを拾わない)。
- **純益**: NO 買い = (1−q)/(1−p+c)−1、YES 買い = q/(p+c)−1。c = 片道コスト = 0.5c(登録値)。
- **ゲート**(全部満たして初めて候補): (G1) 全期間 n≥30 で純益 > 0。(G2) 前半/後半(解決日の中央値で分割)のどちらも純益 > 0 かつ全期間の純益の 1/2 以上(n<30 の半期は判定しない)。(G3) カテゴリ(政治/スポーツ/暗号資産/他)のうち n≥30 のもの全てで純益 > 0。(G4) c を実測スプレッドの半分(価格帯別の中央値、`scripts/books.py`)に置き換えても純益 > 0(実測が 0.5c 未満なら 0.5c のまま)。(G5) 時刻の基準 2 通りで G1 を満たす — A: 登録済みの代理(最後に 0.02<p<0.98 だった時刻)、B: 事前に分かる予定終了日 endDate の T 日前(その時点で未解決の市場のみ)。A は将来の価格経路を使って基準時刻を決めるため実際には執行できず、B を加える。
- **判定**: 合格 = G1〜G5 を満たし、かつ純益の 95% 下限 > 0。下限は (i) イベント単位のクラスタ・ブートストラップ(同一イベント内の市場は独立でないため、2,000 回)と (ii) 実現率の Clopper–Pearson 片側 95% 限界(外れ 0 件なら ≈ Rule of three 3/n)のうち厳しい方。保留 = 点推定では G1〜G5 を満たすが下限 ≤ 0。不合格 = G1〜G5 のいずれかを満たさない。
- **データ整備(バグ修正、結果を見る前に決定)**: (a) outcomePrices が 1/0 でない市場(50/50 解決・取消)は除外し件数を報告(登録版は 0.5 を NO 扱いしていた)。(b) カテゴリ正規表現に語境界を付ける(登録版は `eth`⊂"whether"・"method"、`sol`⊂"resolution" が暗号資産、`war`⊂"award" が政治に入る)。語のリストは変えない。(c) feesEnabled の市場は件数を報告し、手数料を差し引けない場合は除外。
- 月次窓の一覧が 2,000 件(offset 上限)に達した月は切り詰めが起きているので、その月を半月窓で取り直して補う(収集範囲の補完であり条件の変更ではない)。

## 追補4 (2026-11-04): 再収集で見つかった収集上の欠陥と修正(全期間の結果を見る前に記録)
`collect2.py` の再実行で、登録版の収集に 3 つの欠陥が見つかった。いずれも仮説・閾値には触れず、データの取り方だけを直す。
1. **月次窓の切り詰め**: 2025-03 以降は毎月ちょうど約 2,000 件で止まり(offset 上限)、2026-01〜09 は月次窓の要求そのものが HTTP 500 で 0 件だった。登録版の「38,415 件」は母集団ではなく「各月で後に閉じた順に最大 2,000 件」の偏った部分集合だった。→ `collect3.py`(2025-03〜2026-11 を日次窓で)と `collect5.py`(日次でも 2,000 件に達した日を窓の二分割で)で一覧を取り直す。日次の出来高 ≥ $10k の解決市場は 2026 年には 1 日 1,000〜2,000 件あり、大半は暗号資産の「Up or Down」(15 分〜4 時間)・日次の価格帯市場。
2. **価格履歴が空**: CLOB `prices-history` は解決済みの古い市場で `interval=max` が空(`{"history":[]}`)を返す。`startTs/endTs` は幅約 15 日が上限(それより長いと "interval is too long")。→ `collect4.py` は closedTime から 14 日窓で遡り、min(最後に 0.02<p<0.98 だった時刻, endDate) の 31 日前まで(最大 10 窓)を集める。並列 4・各要求後 0.25 秒待ち。
3. **規模**: 母集団は数十万件で、全件の履歴取得は数十時間かかる。→ `sample.py` で標本を作る。寿命(endDate − startDate)が 1 日未満の市場は T≥1 日前の価格を持ち得ず、どのセルにも入らないため枠から外す(損失なし)。残りを endDate の月で層に分け、固定シード(20261104)で各月から一様に最大 2,000 件を抽出する。これで登録版の規模(各月最大 2,000 件)は保ち、「後に閉じた順」の偏りは除く。各月の母数・抽出数は `sample_frame.json` に残す。
- 執行面: `books.py` の厚みを株数で記録し、NO 買いの支払額 (1−bid)×株数 と YES 買いの支払額 ask×株数 に換算するよう修正(初版は p×株数 で、ロングショット帯の NO 買い容量を約 30 分の 1 に過小評価していた)。YES 板と NO 板は鏡像(YES の bid 0.999 × 799,236 株 = NO の ask 0.001 × 同株数を確認)なので、YES 板だけで両方向が分かる。
